# Remediation verification flow — design and first execution

**2026-09-14. Operator-authored, nonauthorizing.** The audit product must verify remediations, not
only find defects: competing services review a fix package and pronounce on its correctness, and a
customer who receives findings without a way to close them has received half a service. This
document defines the flow, records what the engine can do today, what it cannot, and the first
execution against the ForestRoadVault Medium-fix package of 2026-09-14.

---

## What a remediation package asserts, and what verifying it means

A remediation package makes four distinct kinds of claim. Each needs a different check, and a flow
that conflates them produces a green tick that means nothing:

| Claim kind | Example from the 09-14 package | What verification means |
|---|---|---|
| **Identity** | "156 current source files, SHA-256 listed" | The bytes under test are the bytes described. Cheap, deterministic, must be exact. |
| **Validation evidence** | "3,888 test cases, 46 mutation checks, 13 fork tests, gates pass" | Independent re-execution reproduces the numbers. Not "the doc says so". |
| **Defect closure** | "C2 fixed: the reserve records each shortage once" | The specific defect, at its specific location, no longer holds — **and the fix did not introduce a neighbour**. This is the judgment task. |
| **Residual scope** | "C1 remains conditional High; PIK cap remains conditional Medium" | The package's own statement of what it did *not* fix is accurate and complete. Silence about a known defect is the failure mode here. |

## The three legs

### Leg A — Identity and validation re-execution (engine-free, operator-executed)

1. Recompute every hash in the package's source manifest against the working tree. Any mismatch
   halts the flow: the package describes different bytes than the ones being verified.
2. **Diff against the audit pin, not the package's own base.** The remediation team diffs against
   the commit they branched from; the verifier diffs against the commit the audit *saw*. On 09-14
   these differ: the package counts 20 changed sources, the audit-pin diff shows 23. The three
   extra files changed between audit and remediation with no audit coverage at all, and belong in
   scope.
3. Re-run the claimed validation with the package's stated toolchain and compare counts. A
   partitioned result ("2,018 + 77 rerun") is reported as partitioned, never re-summed into a
   single green run.

### Leg B — Post-fix re-audit differenced against pre-fix claims (engine, available today)

Run the standard ensemble over the changed-file set at the post-fix commit, with the same panel
and policy as the original audit, then difference the two claim sets per file:

| Pre-fix | Post-fix | Reading |
|---|---|---|
| claim at L | same claim at L' | **persists** — the fix did not address it, or addressed a different thing |
| claim at L | absent | **not re-raised** — *consistent with* a fix; **not proof of one** (see limits) |
| absent | new claim | **new** — a candidate regression, needs the same review as any finding |

### Leg C — Claim-directed judgment (engine, **not available today**)

For each closure claim in the package, hand the reviewers the original finding, the diff, and the
post-fix file, and ask the judgment question directly: *is the defect at this location closed, and
did the change introduce another?* This is the ensemble's existing judgment stage — reviewers
opine `SUPPORTED` / `REFUTED` / `INCONCLUSIVE` on a claim — with the claim supplied by the
verifier rather than generated by the candidate.

**The engine refuses this.** `development judge-manifest` accepts only a
`DevelopmentCorpusObservation` — a full paid candidate artifact with accounting, routing evidence
and response hashes, bound to the same manifest (`development_cli.py:392-408`: `material.manifest
!= candidate.plan.manifest` is refused). An operator cannot construct a claim set for judgment.
That is the right guard against forged findings, and it is also exactly the gap that makes Leg C
impossible. Raised below as V3-REMEDIATION-001.

## Why Leg B alone is not a remediation verdict

Leg B's "not re-raised" is a fresh-audit result on the new file. It says the candidate model,
reading the fixed file cold, did not produce the same claim. Three things other than a fix produce
that outcome: model variance between runs (the same model produced different claim sets on
identical files during the 09-13 run), the fix moving the defect to a line the same model now
describes differently, and the defect having been a false positive in the first place. Only Leg C
distinguishes them, because only Leg C puts the original claim in front of the reviewer.

Until Leg C exists, the honest verdict vocabulary is: **identity verified / validation reproduced /
not re-raised / persists / new / unverifiable**. "Fixed" is not in it.

## Verdict rules

- Any Leg A identity mismatch → the whole package is **UNVERIFIED**; stop.
- A Leg A validation count that cannot be reproduced → that evidence line is **NOT REPRODUCED**,
  named. The package's other claims are not thereby false, but the package's self-report is no
  longer usable as evidence.
- Per defect: **persists** overrides everything the package says about it.
- A **new** claim at medium or above in a changed file blocks a clean verdict on the file
  regardless of whether the targeted defect was closed.
- The residual-scope section is checked against the pre-fix claim set: every pre-fix
  supported claim in a changed file that is neither closed nor listed as residual is
  **UNACCOUNTED**, and that is a package defect even if the code is fine.

## V3-REMEDIATION-001 — Judge operator-supplied closure claims against a diff

- **Objective:** the judgment stage can only opine on claims the candidate stage produced. A
  remediation verifier needs it to opine on a claim the *verifier* supplies: "defect D at
  `file:L` in commit A is closed by commit B, without regression." Provide a bounded, hash-bound
  input shape for that: pre-fix source, post-fix source, unified diff, the original claim
  (by its retained identity in a prior observation, never free text), and the package's own
  closure statement, all digested and bound into the request identity.
- **Guard to preserve:** the supplied claim must be a *retained* claim from a prior paid
  observation, referenced by observation digest + claim id, so nothing can be judged that was not
  first found by the engine. Free-text operator claims stay refused.
- **Acceptance criteria:** reviewers answer three separately-recorded questions — closed at the
  cited location; regression introduced in the diff; residual statement accurate — each
  `SUPPORTED`/`REFUTED`/`INCONCLUSIVE` with rationale anchored to post-fix lines. Consensus rules
  as for candidate claims. Output is a `remediation_judgment` artifact with the same
  nonauthorizing markers as every development-path artifact.
- **Dependencies:** V3-DEPCLOSURE-001 materially improves this (a fix in a library judged without
  the caller is the same blindfold as before), but is not a prerequisite for the input shape.
- **Provider-free** until exercised.

## First execution — ForestRoadVault Medium-fix package, 2026-09-14

Recorded in the protocol repository at
`audit-reports/corrovera-dual-chain-2026-09-13/REMEDIATION-VERIFICATION-2026-09-14.md` once Legs
A and B complete. Summary of what was run is kept here so the flow's first instance is auditable
from the engine side.

- Leg A identity: **80/80 ETH, 76/76 BSC hashes match** the working trees at `619fe4e` / `8cea113`.
- Leg A scope: audit-pin diff yields **23** changed sources (7 ETH, 16 BSC) vs the package's 20.
- Leg A validation: full non-fork suites re-executed on both trees with Foundry 1.3.2 / solc
  0.8.30; result recorded in the protocol-side report.
- Leg B: 23-file ensemble on ledger-5, panel unchanged from the audit (candidate `z-ai/glm-5.3`,
  reviewers `moonshotai/kimi-k3` and `z-ai/glm-5.2`), three providers, one per leg.
- Leg C: not run; not runnable.
- One further engine defect surfaced on the first launch attempt: `prepare_owned_empty_directory`
  requires the output *parent* to pre-exist and refuses otherwise behind the same generic message
  as every other refusal. Fifth distinct cause now recorded under V3-REFUSALDIAG-001.

## Addendum 2026-09-17 — refutation must be symmetric

The 09-17 diff audit added two stages after Leg B that are now standing parts of the flow, for
both remediation verification and fresh diff audits:

**Stage D — adversarial refutation.** Every medium-or-higher claim, from the ensemble or from
independent readers, goes to two refuters with different briefs (codebase reader; exploit
engineer), each with the whole tree, forge, and permission to write-run-delete probes. Default is
`refuted=true`; a kill must cite the blocking line or a probe. A claim survives only if both fail.

**Stage E — rescue.** Because Stage D is biased toward killing, every killed claim goes to one
rescuer whose only job is to refute the refutation: open the cited counter-evidence line, check it
says what the refuter says, check the guard is on the path the claim describes, check the probe
tested the claim's scenario and not an adjacent one. A rescued claim goes to a probe agent that
settles it by execution. Only then is a claim reported as killed.

Measured on 09-17: 22 ensemble mediums → 1 upheld, 21 killed by both refuters → 0 overturned and
0 narrowed by rescue. The stage costs one agent per killed claim and is what turns "probably
killed" into "killed". Record-keeping caveat found the same day: when two claims share a
`file:line`, label-keyed verdict storage merges them; key by claim index.
